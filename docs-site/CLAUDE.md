# docs-site: public documentation

This directory is the Docusaurus site served at docs.bike4mind.com. It is PUBLIC and auto-deploys to production on every merge to `main` that touches `docs-site/`. Every line you write is published. A private scan gates deploys and, on the PR, `CI Complete` (a late or re-run scan result needs the `Docs Sensitive Scan` job re-run too), but do not rely on it: keep sensitive content out in the first place.

## Never include

- Secrets, keys, tokens, or connection strings with real credentials.
- Cloud identifiers: account ids, ARNs, bucket names, distribution ids, hosted-zone ids.
- Internal hostnames or IP addresses.
- Customer, partner, or teammate names.
- Names of private repositories or internal systems.
- Internal tracker numbers or links (no GitHub issue or PR links, no `owner/repo#N`).
- Premium or overlay feature details.
- Unreleased or roadmap items, and security-finding details.
- Real email addresses, other than the public support address.

Use placeholders instead: `123456789012` for account ids, `example.com` for domains and emails, `<your-api-key>` for secrets, `Acme Corp` for customers.

## What is published

- Everything under `docs/` is published unless it matches the `exclude` list in `docusaurus.config.ts`.
- `features/` and `admin/` are shared with the in-app help corpus and are published too. A page meant only for the in-app help must be added to `exclude` in `docusaurus.config.ts`.
- A new top-level directory under `docs/` needs a deliberate decision: add it to `KNOWN_TOP_LEVEL` in `scripts/check-docs-content.mjs`, and to `exclude` if it is not for the public site. The guard fails otherwise.

## Page format

Read two or three neighboring pages before writing; match them.

1. Front matter at the top of every page: `title`, `description`, `sidebar_position`. Add `tags` where neighboring pages use them.
2. Exactly one H1, matching `title`. Use `##` and `###` below it; do not skip levels.
3. Link to other pages with relative `.md` paths (`./page.md`, `../dir/page.md`). Do not use absolute `/docs/...` links: the site serves at the root and the in-app help renders the same files with relative links. Do not link to GitHub issues or PRs.
4. Images go in `static/img/` with descriptive alt text.
5. Tag every code fence with a language (`bash`, `json`, `ts`, `yaml`, ...).
6. ASCII only: no em dashes, curly quotes, or other smart punctuation. Use `-` and straight quotes.
7. Every directory has a `_category_.json` (label, position, generated-index link).
8. Write in second person, present tense ("You create a notebook"). Plain and factual: no marketing tone, no hype.
9. The sidebar is autogenerated from the filesystem. Do not edit `sidebars.ts` to add a page.
10. The build fails on broken links (`onBrokenLinks: throw`).

## Self-host pages

Pages under `self-host/` must stay faithful to `SELF_HOST.md` at the repo root. Commands must be byte-identical. Change both together.

## Content guard

`scripts/check-docs-content.mjs` rejects generic sensitive shapes (account ids, ARNs, key ids, private key blocks, JWTs, credentialed URLs, token prefixes, `.internal` and `.corp` hosts, non-placeholder emails, tracker references). It runs in CI before the build.

- Fix the content rather than silencing the guard.
- For a verified false positive only, put `<!-- docs-guard-ignore-next-line -->` on the line directly above it.
- Do not add internal names to the script: it is public.

## Before pushing

```bash
cd docs-site && pnpm install --ignore-workspace && pnpm check:content && pnpm build
```

The build must end with `[SUCCESS] Generated static files`. Run `pnpm test:content` if you changed the guard.
