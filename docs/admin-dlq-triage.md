# Admin dead-letter triage

Dead-letter triage proposes an action (replay, discard or investigate) for messages sitting in a registered dead-letter queue. It runs from the queue alarm handler and from the admin dead-letter triage, replay and discard endpoints. It never moves, replays or deletes a message itself.

A recommendation is built from recorded facts only: the consumer's stored failure record for the message (category, transient or terminal-refusal flags, consumer version, failure time), the SQS sent time and queue retention, the registered queue owner, and a small CloudWatch log sample used only when no failure record exists. The SQS view is a partial sample taken with zero visibility timeout, not an inventory of the queue, and every recommendation says so. Message bodies, raw errors, entity IDs and log text are not stored in the evidence. The suggestion's action class is its risk: `terminal-refusal`, `safe-transient` or `review-required`.

A recommendation is shown or sent to Slack only when the AI configuration is enabled, the `dlqTriage` feature and the queue are not off, the feature mode is recommend or act, and `getAdminAiClassReadiness` returns `canRecommend` for feature `dlqTriage`, the suggestion's action class and the current policy version, now `recommend-v2`. That requires the class row to be in recommend or act mode with at least 200 replay cases, at least 90% of them agreed, and a non-empty replay artifact reference. In shadow mode suggestions are stored but not published.

Changing the policy version, as `recommend-v1` to `recommend-v2` did, resets this gate. Readiness is keyed on the policy version, so with no `recommend-v2` class row each action class falls back to shadow and `canRecommend` is false. Every recommendation stays hidden until the new policy has recorded evidence. Stored `recommend-v1` suggestions stay hidden even after v2 is promoted, because the reader also discards any suggestion whose policy version differs from the current one; new suggestions are written under v2 the next time a message is triaged.

To bring a class back after a policy bump, run the replay offline first. This console does not run or verify replays; the counts and artifact reference are entered by an administrator. Then open Admin, AI operations (requires the `settings:manage` permission) and use the "Class evidence and mode" form once for each action class you want published (`terminal-refusal`, `safe-transient`, `review-required`). Set Feature to `dlqTriage`, Action class to the class name, Policy version to `recommend-v2`, the replay artifact reference, replay cases and agreed cases, and Class mode to Recommend. The same form is available as `POST /api/admin/ai-operations`. The server rejects the promotion if the evidence is below the thresholds above. Also confirm under Feature controls that `dlqTriage` is enabled and set to Recommend; moving a feature up to Recommend itself requires existing class evidence. Each change is audited.

Act mode is not available for this feature: there is no registered reversible handler with Undo for dead-letter triage, so `canAct` stays false. Readiness can also demote a class by one rung when more than 10% of recent decided suggestions were overridden.
